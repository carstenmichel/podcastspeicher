- (direction by user) User idea: dockerized app with web UI, Go backend (user knows Go, asked to verify feasibility), React/TS frontend (user preference), scan registered podcast RSS streams, mirror all episodes, never delete, ~6h configurable poll interval, low idle resources, folder structure by podcast name + date; motivation: owners removing old episodes
- (idea by coach) In-browser episode player, podcast-style archive UI in web frontend
- (decision by user) User rejected player idea: UI is ONLY for configuring the podcast registry; no playback
- (idea by user) Metadata + registry stored as Markdown in the same folder structure as downloads (Obsidian-style); whole archive must stay readable if the app dies — future-proof, human-readable, no lock-in
- (decision by user) Chose per-podcast podcast.md (one file per podcast folder) over a central registry file; encapsulation + folder-as-unit-of-work wins, fleet view handled by UI
- (technique) started Six Thinking Hats
- (decision by user) Dedup policy: prefer duplicates over gaps — download when seen, tolerate hand-full of duplicates per podcast; dedupe possible later via sha256
- (decision by user) MUST NOT FORGET: README must explicitly document the feed-truncation limitation (feeds capped at 20-50 items, late subscribers may be unable to catch up on old episodes) with prominent highlighting
- (technique) started Yellow Hats (benefits)
- session resumed after LLM crash; state intact, continuing Six Thinking Hats at Yellow Hats (benefits)
- (decision by user) Core benefit confirmed: the backup is independent of the tool and survives it — the archive outlives the app, so the app is a replaceable appliance
- (idea by coach) Kill drill benefit: stop the container, browse folders, read a podcast.md, play an episode from file path — archive fully legible without the app; design proves itself
- (idea by user) Compact footprint: Go single-binary container, tiny image, consumes almost no resources at idle
- (technique) started Green Hats (creatives, possibilities)
- (idea by coach) Anything can read the archive: plain files + markdown means a static site generator, grep, or Obsidian can turn the whole archive into a browsable website/gallery without the app ever running
- (direction by user) Don't overengineer: reject site-generation/search-corpus extensions; scope stays a lean backup tool, nothing more
- (idea by coach) Only real cut candidate is the React SPA: the registry is already markdown on disk, so the UI could shrink to a single page served by Go (or a CLI) — trades the user's React preference and a comfortable fleet view for no Node build toolchain
- (decision by user) Frontend decision: drop the React SPA; single embedded config page served by the Go binary (go:embed) — enough to configure podcast shows; no Node toolchain
- (technique) convergence started: MoSCoW sort of first-build scope (proposed by coach, user to adjudicate)
- (decision by user) MoSCoW sort approved with adjustments: Must = fetch+download on ~6h poll, never delete, podcast+date folders, per-podcast podcast.md registry with episode GUIDs, config page add/remove show, Docker single-binary image, README feed-truncation warning; Should = fleet status (last fetch/episode count/disk usage), poll interval override
- (decision by user) BACKLOG (later release) item 1: handle feed 404s + rate-limits so a failed fetch is retried on the next poll — demoted out of v1 scope
- (decision by user) BACKLOG (later release) item 2: sha256 content dedupe to clean up the tolerated duplicates — confirmed out of v1
- (decision by coach) Final v1 scope after user adjustment: Should = fleet status (last fetch/episode count/disk usage) + poll interval override only; both 404/rate-limit retry and sha256 dedupe live in the later-release backlog
- (insight) Synthesis: (1) markdown registry + prefer-duplicates-over-gaps + feed-truncation warning are one idea in three hats — the feed is untrustworthy, the disk is the truth; podcast.md is the ledger that outlives the feed's lies. (2) The rejections (no player, no React, no site/corpus, 'don't over engineer') are the design: shrink the tool until only files remain; the kill drill works because every rejected feature would have moved value back into the tool. (3) Prefer-duplicates-over-gaps is an insurance policy, not a data policy — the system is built for the day the feed disappears. Chosen direction: single Go binary + embedded config page, v1 scope per approved MoSCoW, two-item later-release backlog
